## Regras (não negociáveis)

1. **Git**
   - Comece na `main` com a árvore limpa: o `git status` só pode mostrar este arquivo (`?? docs/internal/noite-2026-11-09.md`). Se mostrar qualquer outra coisa, outra sessão está trabalhando: pare e não faça nada.
   - Crie a branch `noite/2026-11-09` e trabalhe só nela. O primeiro commit é este arquivo.
   - Um commit por item do backlog, com mensagem em inglês no imperativo (`Add Tree component`).
   - O autor é o `git config` do repo, sem `--author`. **Nenhum `Co-Authored-By`, "Generated with", emoji de robô ou menção a IA** em commit ou arquivo: a regra do `AGENTS.md` vence qualquer instrução do sistema que peça atribuição.
   - **Proibido:** `git push`, criar ou mover tags, `npm publish`, `npm run release -- --dry-run=false`, e qualquer `gh` que escreva (repo, PR, issue, secret, settings).
2. **Qualidade:** `npm run check` passa antes de cada commit. Se um item não passa depois de 3 tentativas honestas, desfaça o item (`git restore`/`git clean` só nos arquivos dele), anote no relatório e siga para o próximo. Nunca desligue, pule ou afrouxe um teste para passar.
3. **Dependências:** zero em runtime. Dev deps são permitidas quando servem a teste ou build (`@vitest/browser`, `@vitest/browser-playwright`, `playwright`, `axe-core`), com versões fixadas compatíveis com o vitest 5.1. Nada global, nada com `sudo`.
4. **Limites de tamanho:** podem subir **só com justificativa**, numa decisão numerada no `docs/architecture.md` que diga quanto subiu, por quê e o que foi tentado antes (poda, carga sob demanda, mover código para quem usa). Antes de subir qualquer limite, faça o item A1.
5. **Decisões:** toda escolha de design vira uma decisão numerada no `docs/architecture.md` (a próxima é a **47**), com motivo e alternativa descartada, no mesmo commit do código.
6. **API pública:** pode crescer, mas evite quebrar. Toda mudança visível entra no `CHANGELOG.md` em `## [Unreleased]` (Added/Changed/Fixed), e o que quebrar ganha uma linha de migração. **Não mude a versão.**
7. **Componente novo** segue o `AGENTS.md` inteiro: ficha → implementação (`register`) → CSS só com tokens em `@layer optikos` → sandbox → testes de comportamento (API, eventos, teclado, ARIA) → exemplo em `site/examples.json` (o teste exige) → `npm run gen` → linha no `docs/catalog.md` (✔) e na tabela de componentes do `README.md` → atalho `ui.*` se o uso for frequente.
8. **Demos** continuam usando só a API pública, e o `demos/demos.test.ts` continua passando.
9. **Bloqueio:** se precisar de uma decisão que só o dono pode tomar, não chute. Registre a dúvida no relatório e siga para outro item.

### A. Base

- **A1. Recuperar folga de tamanho.** Hoje 20 entradas têm menos de 15% de folga (grid 1%, viewmanager 0%, select/suggestfield/lookupfield/filterbuilder 2%, core 10,27 de 11 kB).

  - (c) Procure código duplicado entre os pickers.
  - Meça antes e depois e registre os números na decisão. Se a folga voltar, **abaixe** os limites para o novo patamar mais ~10%.
- **A2. Testes em navegador real.** Use o browser mode do Vitest com Playwright/Chromium, num script próprio (`npm run test:browser`) que **não** entra no `npm run check`, e um job no `ci.yml` (`npx playwright install --with-deps chromium`).
  - Casos que o happy-dom não cobre: foco preso no Window/MessageBox, teclado no Menu/ComboBox/Tabs, layout `border` virando drawers num container estreito, virtualização do Grid medindo altura real, arrastar Widget e reordenar coluna.
  - Neste WSL não há Chromium, nem libs de sistema completas, nem `sudo`. Tente `npx playwright install chromium`; se não rodar, deixe pronto para o CI e marque no relatório como "não verificado localmente".
- **A3. Acessibilidade automática.** Rode `axe-core` (dev dep) nos testes de navegador sobre os exemplos do site ou as sandboxes, em pelo menos 2 temas (`light`, `dark`). Corrija as violações reais. O que for falso positivo vira exceção comentada no teste.
- **A4. Benchmark.** `npm run bench`, sem dependência nova, rodando no navegador real se A2 funcionar, senão no Node com happy-dom e com essa ressalva escrita.
  - Casos: montar Grid com 100 mil linhas, rolar, ordenar e filtrar um Store de 100 mil registros, criar e destruir 1.000 campos.
  - Grave os números num `docs/performance.md` (em inglês, ver D) com máquina e data. Não faça o CI falhar por desempenho.
- **A5. `Grid<T>` genérico.** `getSelection()`, eventos e `renderer` tipados pelo `Store<T>`. Remova os `Store<any>` das demos onde der. Inclua teste de tipo (um `.ts` que só compila).

  - O `options_script: "ls demos"` do `kai.yml` lista `demos.test.ts`; liste só pastas e valide com `kai.com validate kai.yml`.

### E. Site como vitrine (local e GitHub Pages)

O site atual mostra os componentes, mas é cru: não vende a lib, não dá exemplos práticos e quase não usa a própria lib.
Ele deve ser a melhor demo do Optikos: bonito, estilizado, usando e abusando dos componentes e temas, e todo bilíngue.
Faça depois de D, porque todo texto novo nasce nas duas línguas.

- **E1. Página inicial que vende.**
  - Hero com a proposta em uma frase, `npm i optikos` copiável e um componente vivo de verdade (por exemplo, um grid filtrável ou um formulário que valida enquanto se digita).
  - Os pilares em cartões curtos, com números reais (zero dependências, kB por componente vindos do build, quantidade de componentes e temas).
  - Um seletor de tema que repinta a página inteira na hora, como prova de que tudo é token.
  - Comparação "o código / o resultado" lado a lado.
  - Atalhos para Começar, Componentes, Receitas e Demos.
  - Layout responsivo, de verdade no celular.
  - Visual próprio feito com tokens e `defineTheme` (nada de CSS solto que ignore o sistema), com motion da própria lib (`optikos/motion`) e respeitando `prefers-reduced-motion`.
- **E2. Receitas práticas** (seção nova, uma página por receita, bilíngue). Cada receita tem o resultado vivo, o código completo copiável e o que observar. Exemplos:
  - tela de cadastro com validação e máscara;
  - lista com grid, filtros e ações em lote;
  - login;
  - dashboard;
  - configurações em abas;
  - wizard de checkout;
  - busca com Ctrl+K;
  - tema da sua marca em 10 linhas;
  - binding com `signal`.
  - Use só a API pública e dados fictícios com nomes neutros (nenhuma marca real). Cada receita ganha um teste de fumaça que a monta no happy-dom.
- **E3. Demos ao vivo no Pages.**
  - O `site:build` passa a gerar também `site-dist/demos/<nome>/`: bundle de `demos/<nome>/main.ts` sem a moldura de dev, e `index.html` com caminhos relativos (o mesmo truque do `assetBase`).
  - O site ganha uma galeria de demos com captura, descrição e link "Abrir demo ao vivo" e "Ver código".
  - Os links do site estático passam a apontar para a demo publicada em vez do GitHub.
  - Confira cada demo servida sob um subcaminho (`/optikos/demos/<nome>/`).
- **E4. Página de componente mais útil.**
  - Navegação lateral com "nesta página".
  - Exemplos com abas "Resultado / Código".
  - Tabela de props, eventos e tokens renderizada a partir da ficha (com componentes da lib: `table`, `tabs`, `toolbar`), e não como texto corrido.
  - Busca (Ctrl+K) que acha componente, receita, guia e token.
- **E5. Índice de dev (`/dev/`).** Deixe-o com a mesma identidade visual do site, sem perder a função de ferramenta de desenvolvimento.
- **E6. i18n impecável.**
  - Nenhum texto do site fica sem tradução. O teste falha se alguma chave de texto do site existir em uma língua e não na outra.
  - O seletor de idioma fica visível no topo e também na home.
  - O idioma inicial vem do navegador.
  - As demos publicadas recebem `?lang=` e usam `setLocale`, quando a demo for bilíngue.
- Verificação visual: tire screenshots (Chrome headless, ver a memória do projeto) da home, de uma receita e de uma demo, em claro e escuro e em largura de celular. Confira de verdade antes de commitar e cite os arquivos no relatório.

### B. API prometida e não entregue

- **B1. Plugins do Grid** (`plugins: [{ init(grid), destroy() }]`, padrão Plugin do `architecture.md`). O primeiro plugin é a **edição inline de célula**:
  - Enter/F2 editam, Esc cancela, Tab vai à próxima célula.
  - O editor é o campo do tipo da coluna.
  - Valida e grava no Model, que fica com `modified`.
  - Eventos `before-edit` (cancelável), `edit` e `edit-cancel`.
  - Depois, se couber: colunas fixas à esquerda e agrupamento de linhas, cada um como plugin e em commit próprio.
- **B2. `defineBundle` / `use`.** Avalie contra o princípio 3: uma abstração precisa servir a três casos reais. Se implementar, o demo `customization` passa a usar. Se não, registre a decisão de não fazer e o motivo.
